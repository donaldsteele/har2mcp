# Generated servers

`har2mcp generate` turns a spec into the source code of an MCP server
written in Go. You build it once with the Go toolchain and get a single
program that Claude Code, Claude Desktop or any other MCP client can start.

```sh
har2mcp generate nas.spec.yaml --target go
cd nas-mcp
go build -o nas-mcp .
```

On Windows, build with `go build -o nas-mcp.exe .`.

## What gets written

| File | What it is |
|---|---|
| `go.mod` | The Go module. Its path is `--module`, or `<name>-mcp` by default. |
| `main.go` | Starts the MCP server over stdio and registers the tools. |
| `client_gen.go` | The HTTP client: cookies, login, tokens, logging in again, TLS. |
| `files_gen.go` | The file folder rules, streaming uploads and streaming downloads. |
| `browserlogin_gen.go` | Only when `auth.mode` is `browser`: the headless Chrome login. |
| `tools_gen.go` | One input type and one handler per enabled tool. |
| `custom.go` | Your own code. Created once, never overwritten. See [custom.go](#customgo-your-own-code). |
| `README.md` | The environment variables, how to build, and how to register the server with Claude. |

The `*_gen.go` files, `main.go` and `go.mod` start with
`// Code generated by har2mcp; DO NOT EDIT.` and are rewritten every time you
run `generate`. The code is gofmt-formatted and passes `go vet`. `generate`
refuses to overwrite a file in the output folder that lacks that header (or,
for `README.md`, its own marker), so pointing `-o` at the wrong folder can't
clobber your code.

Its dependencies are the Go standard library, the official MCP Go SDK
(`github.com/modelcontextprotocol/go-sdk`), and in browser mode chromedp.
`generate` runs `go mod tidy` in the output folder to fetch them, unless you
pass `--no-tidy`. If `go` isn't on your `PATH`, `generate` still writes the
files and tells you to install Go and run `go mod tidy` in the folder.

You need Go 1.26 or later to build the server.

## Environment variables

The server reads the device's address and the login from environment
variables when it starts, so the source code never contains them. `<P>` is
the service name in upper case.

| Variable | Purpose |
|---|---|
| `<P>_URL` | The device's address, for example `http://192.168.1.10` or `https://192.168.1.10:5443`. Only the scheme, host and port are used. If it isn't set, the server uses the address recorded in the spec's `service.base_url` |
| `<P>_USER` | Username |
| `<P>_PASSWORD` | Password |
| `<P>_INSECURE` | `1` skips TLS certificate verification, for devices with self-signed certificates |
| `<P>_FILES_DIR` | The only folder that file tools may use. Default: `~/har2mcp-files/<name>`, created when first needed. A leading `~` means your home folder |
| `<P>_BROWSER` | Browser mode only: the path to Chrome, Chromium or Edge, if the server can't find one |

`nas-mcp --help` prints these variables and the `claude mcp add` line, and
`nas-mcp --version` prints the version. The server takes no other arguments.

## Connect it to Claude

Claude Code:

```sh
claude mcp add --transport stdio --env NAS_URL=http://192.168.1.10 --env NAS_USER=admin --env NAS_PASSWORD=your-password nas -- /path/to/nas-mcp/nas-mcp
```

Add `--env NAS_INSECURE=1` for a self-signed certificate, and
`--env NAS_FILES_DIR=/path/to/folder` to choose the files folder. Check that
it connects with `claude mcp list`.

Claude Desktop: add the server to `claude_desktop_config.json` (Settings >
Developer > Edit Config) and restart Claude Desktop.

```json
{
  "mcpServers": {
    "nas": {
      "command": "/path/to/nas-mcp/nas-mcp",
      "env": {
        "NAS_URL": "http://192.168.1.10",
        "NAS_USER": "admin",
        "NAS_PASSWORD": "your-password"
      }
    }
  }
}
```

On Windows, use the full path to `nas-mcp.exe`, with each backslash
doubled in JSON: `"C:\\Users\\you\\nas-mcp\\nas-mcp.exe"`.

Other MCP clients: configure a stdio server whose command is the built
program, with the environment variables above.

The server uses stdio only. It doesn't open a network port.

## Logging in

The server logs in the first time Claude calls a tool, the way the spec's
`auth` block says:

- **`http` mode:** it sends the recorded login request with `{{username}}`
  and `{{password}}` replaced by `<P>_USER` and `<P>_PASSWORD`, and keeps the
  session cookies.
- **`browser` mode:** it starts headless Chrome, opens `auth.login.page_url`,
  fills in the recorded username and password fields, clicks the submit
  button, waits for the session cookie, and copies the cookies into its HTTP
  client. Google Chrome, Chromium or Edge must be installed on the computer
  that runs the server. Set `<P>_BROWSER` if it isn't in a standard place.

After that it sends the session cookies with every request and copies tokens
as `auth.session.tokens` describes, for example a CSRF token from the login
response into an `X-Csrf-Token` header, or an access token into an
`Authorization` header after the token's `prefix` (`Bearer `).

When a response has a status listed in `auth.relogin_on` (usually 401 and
403), or a body containing `auth.relogin_body_contains`, the server logs in
again and retries the call once. A session that expired overnight is
renewed without Claude noticing.

## Tools

Every tool in the spec with `enabled: true` becomes one MCP tool:

- **Name and description** come from the spec.
- **Arguments** come from `inputs`, with their types, descriptions and
  whether they are required.
- **Hints:** `kind: read` sets `readOnlyHint`, and `kind: destructive` sets
  `destructiveHint`. They tell the MCP client what the tool does. They
  don't stop anything: a destructive tool runs when called.

When Claude calls a tool, the server merges the arguments into the request's
fixed values (dotted fields like `config.name` set nested keys), sends it,
and returns the response body as text.

- A response bigger than 100000 bytes is cut there, and the result ends with
  the line `[truncated: <N> bytes total]`.
- A response with a status outside 2xx comes back as an error result with
  the status and the first 2000 bytes of the body, so Claude can see what
  went wrong.

## Files

Upload and download tools work with files on the computer that runs the
server, inside one folder: `<P>_FILES_DIR`, by default
`~/har2mcp-files/<name>`.

- **Uploads** stream a local file to the device as multipart form data,
  without loading it all into memory.
- **Downloads** stream the response straight to a local file.
- **Both return** a small JSON result with the path, the number of bytes and
  the content type, never the file contents. Large files never pass through
  Claude. Upload results also carry the device's HTTP status and the first
  2000 bytes of its answer.

Paths are relative to the folder. A path that would leave it is refused
with an error result, and nothing is read or written. That includes `..`
segments (`../../etc/passwd`), absolute paths outside the folder, and
symlinks that point outside it. "Full control" means control of the device,
not of your disk.

To give Claude a file to upload, put it in the folder first. Downloaded
files appear there too.

## custom.go: your own code

`custom.go` is created the first time you run `generate` and is never
overwritten. The server calls its `registerCustom` function after it has
registered the generated tools, so you can add tools, replace a generated
one (adding a tool with the same name replaces it), or remove one.

```go
package main

import (
	"context"
	"fmt"

	"github.com/modelcontextprotocol/go-sdk/mcp"
)

type systemInfoInput struct{}

// registerCustom runs after the generated tools are registered.
func registerCustom(s *mcp.Server, c *Client) {
	mcp.AddTool(s, &mcp.Tool{
		Name:        "get_system_info",
		Description: "Model, firmware version and uptime of the NAS.",
		Annotations: &mcp.ToolAnnotations{ReadOnlyHint: true},
	}, func(ctx context.Context, req *mcp.CallToolRequest, in systemInfoInput) (*mcp.CallToolResult, any, error) {
		status, body, _, err := c.Do(ctx, "POST", "/module/api.php", nil, "json", map[string]any{"act": "getsysinfo"})
		if err != nil {
			return nil, nil, err
		}
		if status != 200 {
			return nil, nil, fmt.Errorf("NAS answered %d", status)
		}
		return &mcp.CallToolResult{
			Content: []mcp.Content{&mcp.TextContent{Text: string(body)}},
		}, nil, nil
	})

	// Remove a generated tool you never want Claude to call.
	s.RemoveTools("reboot")
}
```

`c.Do` sends a request through the generated client, so it gets the same
login, cookies, tokens, retry and TLS handling as the generated tools:

```go
func (c *Client) Do(ctx context.Context, method, path string, query url.Values, bodyType string, body map[string]any) (status int, respBody []byte, header http.Header, err error)
```

`bodyType` is `none`, `json`, `form` or `multipart`, as in the spec.

To switch a generated tool off, `enabled: false` in the spec is usually
simpler than removing it in `custom.go`.

## Regenerating

After you edit the spec or analyze a new recording, run `generate` again
into the same folder and rebuild:

```sh
har2mcp generate nas.spec.yaml --target go
cd nas-mcp
go build -o nas-mcp .
```

Restart the server in your MCP client to load the new build (in Claude
Code, start a new session).
